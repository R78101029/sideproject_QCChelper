# QCC Helper — 需求規格書

## 1. 產品概述

**QCC Helper** 是一套協助醫院同仁執行品管圈（Quality Control Circle）活動的 Web 工具。同仁可依照品管圈十大步驟，逐步填寫表單、上傳數據、透過 AI Agent 協助分析，最終產出符合醫院繳交要求的成果報告。

### 1.1 設計理念 — 助力而非阻力

> **系統是來幫忙的，不是來考試的。**

醫院同仁的主業是臨床工作，品管圈是額外負擔。系統設計必須遵循以下原則：

| 原則 | 說明 |
|------|------|
| **隨時可存、隨時可走** | 任何頁面、任何狀態都能儲存離開，下次回來繼續。沒填完的就留著，不強迫。 |
| **自由跳步、不鎖流程** | 十大步驟可以任意順序填寫。系統建議順序但不強制。同仁知道自己在做什麼。 |
| **提示而非阻擋** | 缺漏的欄位用**溫和提示**（黃色提醒），不用**紅色錯誤阻擋**。只有最終匯出報告時才列出缺漏清單。 |
| **AI 主動幫填** | AI 不只是「給建議」，要能**直接幫同仁產生草稿內容**填入表單，同仁確認即可。 |
| **能上傳就不打字** | 已有現成 Excel/Word/圖片的，上傳後系統自動擷取，同仁只需確認。 |
| **管理員一眼看到重點** | 管理員不需要點進每個圈隊，首頁就能看到「誰卡住了、誰快到期」。 |
| **漸進完善、最終才要完美** | 過程中允許粗糙、不完整。品管圈本來就是邊做邊改，系統要配合這個節奏。 |

## 2. 目標使用者與角色

| 角色 | 說明 | 權限範圍 |
|------|------|----------|
| 圈隊代表 | 各科室品管圈圈長或指定代表，負責填寫與管理該圈專案 | 建立/編輯/檢視自己圈的專案、上傳檔案、使用 AI Agent、匯出報告 |
| 品管圈管理員 | 品管中心輔導員或管理者，負責審核與指導所有圈隊 | 檢視/評論所有專案、審核步驟成果、管理圈隊帳號、檢視統計報表 |
| 網管（系統管理員） | 資訊部門人員，負責系統維護與帳號管理 | 所有權限、帳號 CRUD、系統設定、資料備份、API 金鑰管理 |

## 3. 核心功能需求

### 3.1 專案管理

| 功能 | 說明 |
|------|------|
| 建立專案 | 輸入圈名、科別、活動期間即可建立。其餘資訊（圈員名單、圈徽等）之後再補 |
| 從範本建立 | 選擇範本後一鍵建立，已有示範內容可參考 |
| 專案列表 | 查看所有進行中/已完成的 QCC 專案 |
| 進度總覽 | 十個步驟的填寫進度一目了然，點擊任一步驟直接跳入 |

**專案總覽頁面設計：**

進入專案後的首頁，以視覺化方式呈現十步驟進度（非表格）：

```
步驟一 ██████████ 100%  ✅
步驟二 ████████░░  80%  🔵
步驟三 ██████░░░░  60%  🔵
步驟四 ████░░░░░░  40%  ← 目前主要在做
步驟五 ░░░░░░░░░░   0%
 ...
```

- 點擊任一步驟即可跳入
- AI 健康度摘要顯示在右側（如有建議的話）
- 「距離活動截止還有 X 天」提示（不是警告，只是資訊）

### 3.2 十大步驟 — 各步驟表單欄位與上傳需求

---

#### 步驟一：組圈

**表單欄位：**
- 圈名
- 圈徽（圖片上傳）
- 圈的意義說明
- 科別 / 單位
- 活動期間（起迄日期）
- 圈長姓名、職稱
- 輔導員姓名、職稱
- 圈員名單（姓名、職稱、角色分工）

**上傳區：**
- 圈徽圖片（PNG/JPG）

**AI Agent 協助：**
- 依科別與主題建議圈名
- 產生圈的意義說明草稿

**成果物：** 組圈登記表

---

#### 步驟二：主題選定

**表單欄位：**
- 候選主題清單（至少 3 個主題，含簡述）
- 評價項目（預設：上級政策、重要性、迫切性、圈能力、可行性，可自訂）
- 評價矩陣（每位圈員對每個主題 × 每個評價項目打分，5/3/1 分制）
- 選定主題名稱
- 選題理由（文字說明）
- 衡量指標定義（如：跌倒次數、等候時間等）

**上傳區：**
- 相關佐證資料（PDF/圖片，如：異常事件統計、投訴紀錄）

**AI Agent 協助：**
- 依候選主題產生選題理由草稿
- 自動計算評價矩陣加總與排序
- 建議衡量指標

**成果物：** 主題選定評價表、選題理由書

---

#### 步驟三：活動計畫擬定

**表單欄位：**
- 各步驟預計起迄日期
- 各步驟負責人
- 開會頻率
- 預計活動總週數

**AI Agent 協助：**
- 依總週數自動建議各步驟時程分配（建議比例）：
  - 步驟 1~6（P 階段）：佔 30%
  - 步驟 7（D 階段）：佔 30%
  - 步驟 8~9（C 階段）：佔 20%
  - 步驟 10（A 階段）：佔 10~20%
- 產生甘特圖（虛線＝預定進度、實線＝實際進度）
- 注意：「解析」與「對策擬定」不可重疊；「效果確認」與「標準化」不可重疊

**成果物：** 甘特圖、活動計畫書

---

#### 步驟四：現況把握

**表單欄位：**
- 查檢期間（起迄日期）
- 查檢項目名稱清單（即缺失類別，如：未洗手、未確認身份...）
- 查檢總數（分母）

**上傳區：**
- 原始查檢數據（CSV/Excel 檔案）
  - 格式：每列一筆紀錄，欄位包含日期、缺失類別、次數等
- 或手動輸入查檢表數據（表格介面）

**AI Agent 協助：**
- 解析上傳的 CSV/Excel，自動辨識缺失類別與次數
- 自動繪製**改善前柏拉圖**（Pareto Chart）
  - X 軸：缺失類別（依次數由高到低排列）
  - 左 Y 軸：次數
  - 右 Y 軸：累積百分比
  - 標示 80% 線
- 計算各項目佔比與累積百分比，格式如下：

  | 缺失類別 | 次數 | 累計次數 | 百分比 | 累積百分比 |
  |---------|------|---------|--------|-----------|
  | 問題 A  | 45   | 45      | 37.5%  | 37.5%     |
  | 問題 B  | 30   | 75      | 25.0%  | 62.5%     |
  | 問題 C  | 20   | 95      | 16.7%  | 79.2%     |
  | 其他    | 25   | 120     | 20.8%  | 100.0%    |

  - 項目由大到小排列，「其他」放最末
  - 項目數控制在 6~10 個以內
- 找出關鍵少數（vital few）項目（80% 線以內）
- 計算現狀值：不良次數 / 總調查次數 × 100%
- 產生現況描述文字

**成果物：** 查檢表、改善前柏拉圖、現況描述

---

#### 步驟五：目標設定

**表單欄位：**
- 現狀值（自動帶入步驟四數據：不良次數 / 總調查次數 × 100%）
- 改善重點佔比（自動帶入：柏拉圖 80% 線以內的累積百分比）
- 圈能力值（全體圈員自評，0~1 之間）
- 目標計算方式選擇：
  - 自訂目標（手動輸入）
  - 依公式計算：
    - **降低類主題**：`目標值 = 現狀值 −（現狀值 × 改善重點 × 圈能力）`
    - **提升類主題**：`目標值 = 現狀值 +（(1 − 現狀值) × 改善重點 × 圈能力）`
- 計算後目標值（自動計算或手動輸入）
- 目標設定理由（文字說明）

**AI Agent 協助：**
- 自動帶入現狀值與改善重點佔比
- 依公式計算建議目標值
- 產生目標設定說明文字（含計算過程）

**成果物：** 目標設定表（含公式計算過程）

---

#### 步驟六：解析

**表單欄位：**
- 魚骨圖主題（即要分析的問題，如「跌倒率偏高」）
- 大要因分類（預設 4M1E：人 Man、機 Machine、料 Material、法 Method、環 Environment，可自訂）
- 每個大要因下的中要因（文字輸入）
- 每個中要因下的小要因（文字輸入）
- 真因圈選（勾選哪些小要因為真因）
- 真因驗證表：
  - 小要因名稱
  - 驗證方法（文字）
  - 驗證結果（是/否為真因）
  - 佐證說明

**上傳區：**
- 真因驗證佐證資料（圖片/PDF/數據）

**AI Agent 協助：**
- 依主題建議魚骨圖各層要因
- 自動繪製魚骨圖（Fishbone Diagram）
- 建議真因驗證方法

**成果物：** 魚骨圖（特性要因圖）、真因驗證表

---

#### 步驟七：對策擬定

**表單欄位：**
- 對策清單（針對每個真因，5W1H 格式）：
  - 真因（自動帶入步驟六）
  - What：對策方案內容
  - Why：為何採此對策
  - Who：負責人
  - Where：實施地點/範圍
  - When：預計完成日
  - How：具體執行方法
- 對策評價矩陣：
  - 評價項目（預設：可行性、經濟性、效益性，可自訂）
  - 評分（5/3/1 分制，每位圈員打分）
- 採行對策標準（總分門檻）
- 採行/不採行判定

**AI Agent 協助：**
- 依真因建議對策方案
- 自動計算對策評分與排序
- 產生對策擬定說明

**成果物：** 對策擬定一覽表、對策評價表

---

#### 步驟八：對策實施與檢討

**表單欄位：**
- 每項採行對策的實施紀錄：
  - 對策名稱（自動帶入）
  - 實施日期
  - 實施前狀況描述
  - 實施後狀況描述
  - 負責人
  - 實施狀態（進行中/已完成/延遲）
  - 單項對策效果驗證（有效/無效/需修正）
  - 檢討說明

**上傳區：**
- 實施前後對比照片
- 相關文件（如：新版 SOP、教育訓練紀錄、公告等）
- 各對策的效果驗證查檢表數據

**AI Agent 協助：**
- 追蹤進度、提醒逾期項目
- 協助撰寫檢討說明

**成果物：** 對策實施檢討表

---

#### 步驟九：效果確認

**表單欄位：**
- 改善後查檢期間
- 改善後查檢總數（分母）

**上傳區：**
- 改善後查檢數據（CSV/Excel，格式同步驟四）
- 或手動輸入改善後數據

**AI Agent 協助：**
- 解析改善後數據
- 自動繪製**改善後柏拉圖**
- 自動產生**改善前後柏拉圖對比**（兩張並排）
- 計算有形成果：
  - **改善幅度**：`(改善前 − 改善後) / 改善前 × 100%`
  - **目標達成率**：`(改善前 − 改善後) / (改善前 − 目標值) × 100%`
- 產生效果確認說明文字
- 產生**無形成果雷達圖**：
  - 評估項目（預設 6~8 項，可自訂）：QCC 手法運用、溝通能力、團隊合作、問題解決能力、品質意識、責任感、積極性、和諧度
  - 全體圈員對改善前、改善後分別自評（1~5 分）
  - 雷達圖呈現改善前（虛線）vs 改善後（實線）

**成果物：** 改善後柏拉圖、改善前後對比圖、目標達成率計算表、無形成果雷達圖

---

#### 步驟十：標準化與檢討改進

**表單欄位：**
- 標準化項目清單：
  - 對策名稱
  - 標準化內容（文字）
  - 文件編號（如 SOP 編號）
  - 負責維護人
- 檢討與改進：
  - 本次活動優點
  - 本次活動待改進事項
  - 下期活動主題建議

**上傳區：**
- 標準化文件（PDF，如新版 SOP）

**AI Agent 協助：**
- 依對策內容產生 SOP 草稿
- 產生活動檢討總結
- 建議下期活動方向

**成果物：** 標準化一覽表、SOP 草稿、檢討改進表

---

### 3.3 混合輸入模式（線上填寫 / 文件上傳）

每個步驟皆支援兩種資料輸入方式，同仁可依習慣自由選擇：

| 輸入方式 | 說明 | 適用情境 |
|----------|------|----------|
| **線上填寫** | 透過系統表單逐欄填寫，即時驗證與自動計算 | 從零開始填寫、需要系統自動計算的步驟 |
| **文件上傳** | 直接上傳已完成的文件（Word/Excel/PDF/圖片），系統擷取內容 | 已有現成資料、習慣用 Office 工具處理、跨系統轉移資料 |

**各步驟支援的上傳替代方式：**

| 步驟 | 可上傳替代的內容 | 系統處理方式 |
|------|-----------------|-------------|
| 1 組圈 | 組圈登記表（Word/PDF）、圈員名冊（Excel） | AI 擷取圈名、圈員資訊，自動填入欄位 |
| 2 主題選定 | 評價矩陣表（Excel）、選題理由書（Word/PDF） | AI 解析評分矩陣，自動計算排序 |
| 3 活動計畫 | 甘特圖（Excel/圖片）、計畫書（Word/PDF） | AI 辨識時程資訊，轉為系統甘特圖數據 |
| 4 現況把握 | 查檢表（Excel/CSV）、柏拉圖（圖片） | 解析數據產生柏拉圖；圖片則直接作為成果物 |
| 5 目標設定 | 目標設定表（Word/Excel/PDF） | AI 擷取現狀值、目標值等關鍵數據 |
| 6 解析 | 魚骨圖（圖片/PDF）、真因驗證表（Excel） | 圖片直接作為成果物；Excel 解析填入驗證表 |
| 7 對策擬定 | 對策一覽表（Excel/Word） | AI 解析 5W1H 欄位，填入系統表格 |
| 8 對策實施 | 實施記錄表（Word/Excel）、照片 | 解析填入實施紀錄 |
| 9 效果確認 | 改善後查檢表（Excel/CSV）、雷達圖自評表（Excel） | 解析數據產生柏拉圖與雷達圖 |
| 10 標準化 | SOP 文件（Word/PDF）、檢討報告（Word/PDF） | 直接作為成果物附件 |

**混合模式規則：**
- 同一步驟可同時使用兩種方式（例如：上傳部分欄位的 Excel，再線上補填其餘欄位）
- 上傳文件後，系統顯示 AI 擷取結果的預覽，同仁確認後才寫入
- 上傳的原始文件保留在系統中，作為佐證附件
- 線上填寫的數據優先；若上傳內容與線上填寫衝突，提示同仁選擇

### 3.4 快速工具（成果物快速產生器）

針對報告書需要的成果物，提供簡化的互動工具，讓同仁不需深入操作即可快速產出，數據自動存入系統供報告匯出時直接取用。

#### 甘特圖快速產生器（步驟三）

| 功能 | 說明 |
|------|------|
| 一鍵範本 | 輸入活動起迄日期與總週數，系統依 PDCA 建議比例自動產生排程 |
| 拖拉調整 | 在時間軸上直接拖拉調整各步驟的起迄時間 |
| 自動校驗 | 自動檢查步驟間不可重疊的規則，違規時提示 |
| 實際進度標記 | 活動進行中可隨時更新實際進度線 |

#### 評價矩陣快速計分器（步驟二、七）

| 功能 | 說明 |
|------|------|
| 快速打分介面 | 每位圈員用按鈕點選 5/3/1 分，不需逐格輸入 |
| 即時排名 | 打分後自動加總排序，即時顯示結果 |
| 匯入匯出 | 支援從 Excel 匯入已有的評分表 |

#### 魚骨圖互動編輯器（步驟六）

| 功能 | 說明 |
|------|------|
| 範本起始 | 預設 5M1E 骨架，點擊即可新增中/小要因 |
| 拖拉排列 | 要因可拖拉移動到不同大骨下 |
| 圈選標記 | 點擊小要因即可標記為「圈選真因」（紅圈標示） |

#### 柏拉圖快速產生器（步驟四、九）

| 功能 | 說明 |
|------|------|
| 簡易表格輸入 | 直接在表格中填寫「類別＋次數」，系統自動排序、計算百分比、繪圖 |
| CSV 一鍵匯入 | 上傳 CSV/Excel 後自動辨識並繪製 |
| 圖表微調 | 可調整顏色、標籤、80% 線位置等 |

#### 雷達圖自評工具（步驟九）

| 功能 | 說明 |
|------|------|
| 滑桿打分 | 各評估項目用滑桿（1~5 分）快速評分 |
| 多人彙整 | 全體圈員各自打分後，系統自動計算平均值 |
| 前後對比 | 改善前/後兩組分數自動疊加顯示 |

**數據存取原則：**
- 所有快速工具產生的數據皆以結構化 JSON 存入 Steps.data
- 匯出報告時，系統從 Steps.data 直接讀取並重新渲染圖表
- 同仁也可將快速工具產生的圖表單獨下載為 PNG/SVG

### 3.7 AI Agent 通用功能

| 功能 | 說明 |
|------|------|
| 步驟引導 | 在每個步驟提供說明，告訴同仁「這步要做什麼、怎麼做」 |
| 數據分析 | 解析上傳的 CSV/Excel，自動產生統計與圖表 |
| 圖表生成 | 柏拉圖、魚骨圖、甘特圖、雷達圖等 |
| **一鍵填入草稿** | AI 不只給建議，能**直接產生草稿內容並填入表單欄位**，同仁確認或修改即可 |
| 對話問答 | 同仁可隨時詢問品管圈相關問題 |
| 專案健康度分析 | 綜觀整個專案的填寫狀態，主動提供建議（詳見 3.7.1） |

#### AI 主動協助原則

> AI 的目標是**讓同仁少打字**，而非只是旁邊給建議。

| 情境 | AI 行為 |
|------|---------|
| 同仁進入空白步驟 | AI 主動詢問：「需要我幫你產生這個步驟的草稿嗎？」 |
| 同仁上傳 CSV | AI 自動解析 → 產生柏拉圖 → 填入統計表 → 寫好現況描述，同仁只需確認 |
| 同仁填完步驟四 | AI 提示：「要我幫你計算目標值並填入步驟五嗎？」 |
| 同仁的魚骨圖只有 2 個大骨 | AI 提示：「我可以幫你補充其他面向的要因建議」，但**不強制** |
| 步驟七需要 5W1H | AI 依真因自動產生對策草稿，同仁逐條確認修改 |
| 同仁匯出報告 | AI 自動補齊缺漏的「描述文字」欄位草稿（如現況描述、目標設定理由） |

**關鍵設計：**
- AI 產生的內容一律標記為「AI 草稿」，同仁可一鍵採用、修改或忽略
- 每個步驟表單旁有「AI 幫我填」按鈕，點擊後 AI 依現有數據產生該步驟的完整草稿
- AI 草稿填入後，欄位背景顯示淺藍色，表示「AI 產生、待確認」，同仁編輯後變為正常白色

#### 3.7.1 AI 專案健康度分析與跨步驟建議

同仁在執行品管圈時常在步驟間來回修改，或卡在某個步驟不知如何推進。AI 可綜合分析專案狀態，提供**建議性**指引。

> **原則：AI 健康度是「友善的教練」，不是「嚴格的監考官」。** 提供建議，不評分、不警告。

**觸發方式：**
- 同仁進入專案總覽頁面時，右側顯示 AI 建議（摺疊式，可收合不看）
- 同仁可在任何步驟點擊「問問 AI」按鈕，請 AI 給建議
- **不主動彈出提醒打斷同仁操作**

**建議類型（語氣友善）：**

| 類型 | 範例 |
|------|------|
| 下一步建議 | 「步驟四的數據上傳了，接下來可以到步驟五設定目標，需要我幫你算嗎？」 |
| 補強建議 | 「魚骨圖目前有 3 個面向，如果想更完整，我可以幫你補充其他面向的參考」 |
| 數據提醒 | 「步驟九的查檢類別和步驟四不太一樣，要不要看一下？」 |
| 進度參考 | 「距離活動截止還有 6 週，目前在步驟四，時間上是來得及的」 |

**關鍵：**
- 所有建議都附帶「要我幫你處理嗎？」的行動按鈕，點擊後 AI 直接執行
- 建議可以被忽略或關閉，系統不會反覆提醒同一件事
- 不顯示「健康度分數」或「紅綠燈」等帶有壓力的評分機制

### 3.8 步驟間數據連動

各步驟之間有明確的數據流向，當上游步驟修改資料時，下游步驟需同步處理。

**數據流向圖：**

```
步驟一（圈員名單）──→ 步驟二（評價矩陣的圈員列）
                    ──→ 步驟七（對策負責人選單）
                    ──→ 步驟九（雷達圖自評的圈員列）

步驟四（查檢數據）──→ 步驟五（現狀值、改善重點佔比）
                    ──→ 步驟九（改善前數據，用於前後對比）

步驟五（目標值）  ──→ 步驟九（目標達成率計算）

步驟六（真因清單）──→ 步驟七（對策須對應的真因列表）

步驟七（採行對策）──→ 步驟八（實施紀錄的對策列表）
                    ──→ 步驟十（標準化項目的對策來源）
```

**連動規則（柔性連動）：**
- 上游步驟有數據時，下游步驟的對應欄位**自動帶入**，省去重複輸入
- 上游修改後，下游欄位旁顯示小圖示「上游數據已更新」，同仁**可選擇**是否同步
- 同仁手動修改過的值**永遠不會被自動覆蓋**，優先尊重同仁的判斷
- 同仁可點擊「重新同步」按鈕，主動拉取上游最新數據
- **若上游步驟尚無數據，下游步驟仍可正常填寫**（欄位留空或手動輸入）

### 3.9 步驟完成度與彈性流程

#### 自由導航原則

同仁可以**任意順序**填寫十大步驟，系統不強制線性流程：

- 側邊欄顯示所有 10 個步驟，隨時可點擊切換
- 每個步驟顯示填寫進度環（如 3/8 欄位已填）
- 尚未開始的步驟也可以直接進入填寫
- 步驟間的數據帶入（3.8）在有上游數據時自動填入，沒有時留空讓同仁手動填

#### 完成度提示（非阻擋）

| 機制 | 說明 |
|------|------|
| 進度指示 | 各步驟顯示「已填 X / 共 Y 欄位」的進度，不用紅色警告 |
| 建議標記 | 報告必要的欄位以「建議填寫」標示（藍色星號），而非「必填」 |
| 自由標記完成 | 同仁可隨時將步驟標記為「已完成」，即使有欄位空白。系統僅顯示提示「尚有 N 個建議欄位未填」，但**不阻擋** |
| 匯出前摘要 | 匯出報告前，系統列出所有空白的「建議填寫」欄位作為 checklist，讓同仁自行決定是否補齊。空白欄位在報告中以「—」或「（待補充）」顯示，**不阻擋匯出** |
| 完成度百分比 | 在專案總覽顯示各步驟的填寫進度，供同仁自我掌握 |

#### 快速填寫模式

對於時間緊迫的同仁，每個步驟提供**精簡模式**與**完整模式**切換：

| 模式 | 說明 |
|------|------|
| **精簡模式**（預設） | 只顯示產出報告必要的核心欄位（通常 3~5 個），快速填完 |
| **完整模式** | 展開所有欄位，適合想做到最好的圈隊 |

同仁可隨時切換，精簡模式填過的內容在完整模式中保留。

### 3.17 醫院層級成果輸出與制度提升

品管圈活動不只是個別圈隊的事，醫院管理層關心的是：**全院投入品管圈，到底帶來了什麼實質改善？** 系統必須能產出醫院層級的成果數據，支援評鑑呈報與決策。

#### 3.17.1 評鑑導向的報告輸出

> 醫院最直接的需求：**品管圈成果能不能直接拿去 JCI / 醫院評鑑用？**

| 功能 | 說明 |
|------|------|
| 評鑑摘要報告 | 一鍵產出「品管圈年度成果摘要」，格式對應常見評鑑要求：活動概述 → 量化成效 → 代表案例 → 持續改善計畫 |
| 指標改善對照表 | 自動彙整全院所有圈隊的「改善前 vs 改善後」數據，產出一覽表。評鑑委員一眼可看到全院品質提升成果 |
| 改善主題分布圖 | 各科別、各類型問題的品管圈分布統計（如：病安類 5 圈、流程改善類 8 圈、感控類 3 圈）|
| 範例圈隊精選 | 管理員可標記「代表圈隊」，系統自動將其成果摘要整理為評鑑呈報格式 |

**報告自動產出的關鍵數據：**

#### 3.17.2 全院品質趨勢追蹤

| 功能 | 說明 |
|------|------|
| 年度趨勢圖 | 逐年統計品管圈數量、完成率、平均改善幅度的趨勢折線圖 |
| 科別參與熱力圖 | 各科別歷年參與品管圈的次數與改善成效，一眼看出哪些科別活躍、哪些需要鼓勵 |
| 改善主題詞雲 | 歷年品管圈主題的關鍵字詞雲，識別全院反覆出現的品質問題 |

#### 3.17.3 知識沉澱與經驗傳承

> **做過的品管圈不該做完就消失。** 經驗要留下來，後面的人才能站在前人的肩膀上。

| 功能 | 說明 |
|------|------|
| 全院知識庫 | 所有已完成的品管圈自動歸檔為可搜尋的知識庫，依科別、主題分類瀏覽 |
| 智慧搜尋 | 同仁輸入問題描述（如「門診等候時間太長」），AI 自動找出歷年相似主題的品管圈，摘要呈現做法與成效 |
| 常見真因庫 | 從已完成的魚骨圖中彙整常見真因，新圈隊做解析時 AI 可參考過去同類問題的真因 |
| 有效對策庫 | 從已完成的對策實施中彙整有效對策（改善幅度高的），新圈隊擬定對策時可參考 |
| 跨圈學習 | 同仁可瀏覽其他圈隊的公開成果，學習不同科別的做法（管理員控制公開範圍） |

**AI 知識庫應用情境：**
- 同仁做步驟六（解析）時，AI 提示：「過去護理科的跌倒防治圈，真因分析中發現『交班時段人力不足』和『廁所扶手高度不當』是主要因素，要參考嗎？」
- 同仁做步驟七（對策）時，AI 提示：「過去有 3 個圈隊處理過類似問題，其中效果最好的對策是○○，改善幅度達 60%，要採用嗎？」

#### 3.17.4 效益量化與投資回報

醫院高層最終想知道的是：**品管圈活動值不值得持續投入？**

| 功能 | 說明 |
|------|------|
| 改善效益摘要 | 各圈隊可選填「預估效益」（如：每年節省 X 小時人力、減少 X 件不良事件、節省 X 元耗材成本） |
| 全院效益彙總 | 自動加總全院所有圈隊的填報效益，產出年度效益報告 |
| 效益分類統計 | 依效益類型分類：人力節省、成本節省、品質提升（如不良率下降）、病人滿意度提升 |
| 投入產出對照 | 記錄各圈投入的時間與人力（從活動期間與圈員數推算），與改善效益對照 |

> **設計原則：** 效益欄位為**選填**，不強迫同仁填寫。有填的圈隊自動彙入報告，沒填的不影響。系統可依改善幅度推估效益（AI 輔助），但標註為「系統推估」。

#### 3.17.5 持續改善循環

| 功能 | 說明 |
|------|------|
| 標準化追蹤 | 步驟十產出的 SOP 可標記追蹤期限，到期時提醒管理員確認是否仍在執行 |
| 再發防止確認 | 改善後 3/6/12 個月，系統提醒同仁回填追蹤數據，確認改善效果是否持續 |
| 延續型專案 | 當追蹤發現問題再發，可一鍵從原專案建立延續型品管圈，自動帶入歷史數據 |

> **提醒方式：** 溫和提醒（系統通知 + 管理員月報中列出），不強制。同仁忙碌時可忽略，管理員可視情況追蹤。

## 5. 技術架構

### 5.1 技術棧

```
Frontend:    Next.js 14+ (App Router) + TypeScript + Tailwind CSS
Backend:     Next.js API Routes
Database:    PostgreSQL 16 (開發與正式環境皆使用)
ORM:         Prisma (schema-first, 自動 migration)

AI:          Claude API (對話、分析、文件擷取)

Charts:      ECharts (柏拉圖、魚骨圖、甘特圖、雷達圖)

Export:      jsPDF + pptxgenjs
Deployment:  Docker Compose (Next.js + PostgreSQL + Nginx)
```

### 5.2 技術選型理由

QCC Helper 與同院另一專案 **CQI365 Hospital**（醫療品質管理平台）同時部署於院內 Docker 環境，兩者技術棧有所不同，各有其設計背景：

#### 兩專案技術比較

| 面向 | QCC Helper（本專案） | CQI365 Hospital |
|------|---------------------|-----------------|
| **前端框架** | Next.js 14 (App Router, SSR) | React SPA (Vite) + Nginx 靜態託管 |
| **後端** | Next.js API Routes（內建） | Hono API（獨立 Node.js 服務） |
| **ORM** | Prisma | Drizzle |
| **專案結構** | 單一 Next.js 專案 | Turborepo monorepo（多 app） |
| **資料庫** | PostgreSQL 16 | PostgreSQL 16（相同） |
| **部署方式** | Docker Compose | Docker Compose（相同） |

#### 差異原因分析

**CQI365 Hospital — 遷移型架構**

CQI365 原本建構在 Supabase（雲端 BaaS）上，前端為 React SPA 直接呼叫 Supabase API。後因醫院資安政策，決定遷移至院內 Docker 部署。因此：
- 前端維持 **React SPA** 架構，避免遷移時大幅改寫
- 後端改用 **Hono API** 取代 Supabase Edge Functions，作為獨立服務
- 使用 **Turborepo monorepo** 是因為包含多個子應用（hospital、doctor、admin 等），需要共用程式碼
- 使用 **Drizzle ORM** 搭配 Hono 生態系
- 資料庫有 **49 張資料表**，屬於大型平台

**QCC Helper — 全新設計架構**

QCC Helper 從零開始設計，無歷史包袱，因此選擇更精簡的全端方案：
- **Next.js App Router** 前後端一體，減少服務數量與維護成本
- **Prisma ORM** schema-first 設計，自動產生 TypeScript 型別與 migration，對單一專案開發效率高
- **單一專案結構**，因為只有一個應用，不需 monorepo
- 醫院資訊室未來接手時，只需了解一套框架

#### 技術選型原則

雖然兩專案技術棧不同，但遵循相同的核心原則：

| 原則 | 說明 |
|------|------|
| 零雲端依賴 | 不依賴 Supabase、Firebase、Cloudflare 等外部雲服務 |
| 院內網路部署 | 所有服務運行在醫院內網 Docker 環境，不對外開放 |
| PostgreSQL 統一 | 兩專案共用同一個 PostgreSQL 16 container（不同 database） |
| TypeScript 統一 | 兩專案前後端皆使用 TypeScript，降低維護學習成本 |
| Docker 統一 | 兩專案皆以 Docker Compose 編排，統一啟停與備份流程 |

### 5.4 共用 Docker Compose 結構

```yaml

services:
  # ── 共用基礎設施 ──

  # ── QCC Helper ──
  qcc-app:        # Next.js (:3000)

  # ── CQI365 Hospital ──
  cqi365-app:     # React SPA + Nginx (:5170)
  cqi365-api:     # Hono API (:3100)

volumes:
  pg-data:
  qcc-uploads:
  cqi365-uploads:

networks:
  hospital-net:   # 所有服務在同一內部網路
```

### 5.5 未來遷移路徑

初期以 Docker 自建部署，未來醫院資訊室若要納入正式管理：

| 階段 | 動作 | 說明 |
|------|------|------|
| 1. 資料庫遷移 | `pg_dump` 匯出 → 匯入院內 DB | Prisma / Drizzle 皆支援連線字串切換 |
| 2. 檔案遷移 | uploads volume 複製到新路徑 | Docker volume 可直接 `cp` 或 `tar` |
| 3. 應用部署 | 沿用 Docker 或改為 VM | Next.js / Hono 皆可 bare-metal 運行 |
| 4. 歷年資料 | PostgreSQL 加索引優化查詢 | 品管圈資料逐年累積，需要長期保存 |
| 5. 統一帳號 | 兩專案共用 User 表或接 LDAP | 視醫院資訊室需求決定 |

### 5.6 維運要點

| 項目 | 指令 / 方式 |
|------|------------|
| 啟動所有服務 | `docker compose up -d` |
| 停止所有服務 | `docker compose down` |
| 查看日誌 | `docker compose logs -f <service>` |
| 資料庫備份 | `docker exec postgres pg_dumpall -U postgres > backup.sql` |
| 資料庫還原 | `cat backup.sql \| docker exec -i postgres psql -U postgres` |
| 上傳檔案備份 | `docker cp <container>:/uploads ./uploads-backup` |
| 定期備份建議 | cron job 每日備份 DB + uploads，保留 30 天 |

## 8. API 端點規格

所有 API 端點皆位於 `/api/` 路徑下，使用 Next.js API Routes 實作。

### 8.1 認證 API

| Method | 路徑 | 說明 | 權限 |
|--------|------|------|------|
| POST | `/api/auth/login` | 登入，回傳 JWT token | 公開 |
| POST | `/api/auth/logout` | 登出，清除 cookie | 已登入 |
| GET | `/api/auth/me` | 取得目前使用者資訊 | 已登入 |
| PUT | `/api/auth/password` | 修改自己的密碼 | 已登入 |

### 8.2 專案 API

| Method | 路徑 | 說明 | 權限 |
|--------|------|------|------|
| GET | `/api/projects` | 專案列表（依角色過濾） | 已登入 |
| POST | `/api/projects` | 建立新專案 | team_rep, qcc_admin |
| GET | `/api/projects/:id` | 專案詳情（含所有步驟狀態摘要） | 專案成員 / admin |
| PUT | `/api/projects/:id` | 更新專案基本資訊 | 專案圈長 |
| DELETE | `/api/projects/:id` | 刪除專案（軟刪除，改 status=archived） | sys_admin |
| POST | `/api/projects/:id/clone` | 從範本或現有專案複製 | team_rep, qcc_admin |

### 8.3 步驟 API

| Method | 路徑 | 說明 | 權限 |
|--------|------|------|------|
| GET | `/api/projects/:id/steps` | 取得所有步驟狀態 | 專案成員 / admin |
| GET | `/api/projects/:id/steps/:n` | 取得步驟 n 的完整 data | 專案成員 / admin |
| PUT | `/api/projects/:id/steps/:n` | 更新步驟 n 的 data（自動儲存用） | 專案成員 |
| PUT | `/api/projects/:id/steps/:n/status` | 更新步驟狀態（完成/退回進行中） | 專案成員 |
| GET | `/api/projects/:id/steps/:n/completeness` | 檢查步驟必填項完成度 | 專案成員 / admin |
| GET | `/api/projects/:id/health` | AI 專案健康度分析 | 專案成員 / admin |

### 8.4 圈員 API

### 8.11 API 通用規範

**回應格式：**

```json
// 成功
{ "success": true, "data": { ... } }

// 錯誤
{ "success": false, "error": { "code": "VALIDATION_ERROR", "message": "圈名為必填欄位" } }
```

**錯誤碼：**

| HTTP 狀態碼 | error.code | 說明 |
|------------|------------|------|
| 400 | `VALIDATION_ERROR` | 輸入驗證失敗 |
| 401 | `UNAUTHORIZED` | 未登入或 token 過期 |
| 403 | `FORBIDDEN` | 無權限存取此資源 |
| 404 | `NOT_FOUND` | 資源不存在 |
| 409 | `CONFLICT` | 資料衝突（如帳號重複） |
| 413 | `FILE_TOO_LARGE` | 上傳檔案超過限制 |
| 500 | `INTERNAL_ERROR` | 伺服器內部錯誤 |

## 10. 技術細節補充

### 10.1 認證機制

採用 **JWT + httpOnly cookie** 方案：

| 項目 | 規格 |
|------|------|
| Token 類型 | JWT（HS256） |
| 儲存方式 | httpOnly + Secure + SameSite=Strict cookie |
| 過期時間 | 預設 8 小時（可由 SystemSetting 調整） |
| Token 內容 | `{ sub: user_id, role, iat, exp }` |
| 刷新機制 | 每次 API 請求時檢查剩餘時間，<1 小時自動續期 |

不使用 localStorage 存放 token，避免 XSS 風險。

### 10.2 自動儲存機制

| 項目 | 規格 |
|------|------|
| 觸發方式 | 表單欄位變更後 debounce 3 秒自動觸發 |
| API 呼叫 | `PUT /api/projects/:id/steps/:n`（送出整個 step data） |
| 前端狀態 | 顯示儲存狀態指示器：「已儲存」/「儲存中...」/「未儲存變更」 |
| 衝突處理 | 單一使用者場景為主，不處理多人同時編輯同一步驟的衝突 |
| 離開提醒 | 若有未儲存變更，離開頁面時顯示 `beforeunload` 確認 |
| 失敗重試 | 儲存失敗時自動重試 1 次，仍失敗則顯示錯誤提示並保留本地資料 |

### 10.4 AI Agent System Prompt 設計原則

每個步驟有獨立的 system prompt，結構如下：

```
你是 QCC Helper 的 AI 助理，目前正在協助品管圈的「{步驟名稱}」步驟。

## 你的角色
- 你是品管圈專家，熟悉醫療品質改善流程
- 你的回答應使用繁體中文
- 你應該引導同仁完成此步驟，而非直接替他們做

## 此步驟的目的
{步驟目的說明}

## 此步驟的關鍵要點
{步驟重點與常見錯誤}

## 目前專案資訊
{動態注入：圈名、主題、已完成步驟的關鍵數據}

## 限制
- 不要產生任何病患個資或可識別個人的資訊
- 數據分析時，只處理使用者提供的統計數據
- 文字生成僅為草稿建議，提醒同仁需自行審核修改
```

**動態注入規則：**
- 步驟 5 的 prompt 自動注入步驟 4 的 `current_rate` 和 `vital_few`
- 步驟 7 的 prompt 自動注入步驟 6 的 `confirmed_root_causes`
- 步驟 9 的 prompt 自動注入步驟 4、5 的數據用於對比計算
- 專案健康度分析的 prompt 注入所有步驟的 `status` 和 `completeness`

| 方式 | 用途 | 實作 |

| PNG 下載 | 同仁單獨下載圖表 | `echarts.getDataURL()` |
| SVG 嵌入 PDF | 報告匯出時嵌入 | ECharts SVG renderer → jsPDF |
